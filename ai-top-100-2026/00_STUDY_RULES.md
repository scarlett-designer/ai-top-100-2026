# AI TOP 100 2026 스터디 공통 규칙

> 버전: 1.0.0 · 작성일: 2026-10-06  
> 용도: 예시 문제 출제, 스터디 진행, 답안 피드백의 공통 기준  
> 성격: 대회 개요와 전년도 출제 의도·문제를 분석해 만든 **학습용 기준**. 공식 평가표나 배점이 아니다.

## 1. 문서의 목적과 적용 범위

이 스터디의 목표는 다음과 같다.

> 불완전한 인터뷰와 자료를 받아, 해결할 문제를 선택하고, AI·도구·사람의 역할을 나눈 뒤, 처음 보는 사례에서도 작동하는 에이전트를 완성한다.

이 문서는 기존 스터디 계획·역량 체크리스트를 대체하는 공통 기준이다. 예시 문제를 만들거나 답안을 평가하는 AI와 사람은 이 문서를 먼저 읽고 적용한다.

- 모든 세션은 문제 발견·정의 → 작동 설계 → 구현 → 검증·개선 중 어디를 훈련하는지 명시한다.
- 부분 과제는 해당 단계만 평가한다. 아직 요구하지 않은 구현이나 테스트가 없다는 이유로 감점하지 않는다.
- 전체 사이클 과제는 문제 정의, 작동 구조, 실행 결과, 검증 기록을 모두 요구한다.
- 설명만 작성한 상태와 실제로 실행한 상태를 구분한다.
- 공식 안내와 충돌하는 준비 방식은 최신 공식 안내에 맞춰 수정한다. 공식 규정·학습 규칙·문제 속 가상 운영 규칙을 구분한다.

## 2. 설계 근거

아래 내용은 앞선 대화에서 분석한 자료를 학습 기준으로 정리한 것이다. 출제자의 의도를 확정하거나 올해 심사 기준을 예측한 공식 문서로 사용하지 않는다.

| 분석 자료 | 스터디에 반영할 내용 |
| --- | --- |
| 2026 대회 개요 | 인터뷰로 상황을 파악하고 문제를 정의해 에이전트로 구현한다. |
| 2025 출제 의도 | 사람이 구조를 설계하고 AI의 수행 결과를 검증하며 실패에 개입한다. |
| 2025 실제 문제 | 정보 구조화, 도구 선택, 규칙 적용, 근거 확인, 반복 개선을 직접 수행한다. |

올해 준비에서는 **문제 정의와 에이전트 행동의 연결**을 집중 훈련한다. 사용자의 표면적 요구를 곧바로 기능으로 만들지 않고, 실제 행동과 제약을 확인해 해결할 문제를 선택한다.

프로덕트 디자인 경험은 인터뷰와 사용자 흐름 설계에 활용한다. 에이전트 구현·검증 능력은 별도의 실행 증거로 확인한다. 배경이나 경력만으로 역량을 높게 평가하지 않는다.

## 3. 고정 원칙

아래 원칙은 세션마다 임의로 바꾸지 않는다. 수정이 필요하면 12절의 변경 절차를 따른다.

1. **근거로 문제를 선택한다.** 사실·의견·요구·가설을 구분하고, 자료에 없는 내용을 사실처럼 추가하지 않는다.
2. **필요한 질문을 한다.** 질문이 어떤 판단을 바꿀지 설명한다. 실행에 충분한 정보가 모이면 질문을 멈추고 남은 가정을 명시한다.
3. **실행 가능한 작업으로 분해한다.** 입력, 판단 규칙, 행동, 출력, 예외와 중단 조건을 구체화한다.
4. **역할을 적절히 나눈다.** AI·코드·검색·사람에게 정확성과 비용, 실행 가능성을 고려해 작업을 배분한다.
5. **작은 첫 버전을 일찍 실행한다.** 분석과 설계만 반복하지 않는다. 첫 전체 사이클부터 단일 목적의 최소 에이전트를 완성한다.
6. **입력과 출력을 검증한다.** 외부 자료의 내용을 실행 지시와 구분하고, 답·계산·행동을 근거 및 규칙과 대조한다.
7. **새 사례로 확인한다.** 개발 중 사용한 사례와 별도로 검증 사례를 확보한다. 검증 사례를 보고 수정했다면 최종 확인용 새 사례를 다시 사용한다.
8. **실패 원인을 찾아 수정한다.** 프롬프트를 무작정 늘리지 않고, 실패한 단계와 수정할 대상을 특정한다.
9. **문제 해결까지 확인한다.** 답을 생성했는지와 사용자가 실제 다음 행동을 할 수 있는지를 따로 확인한다.
10. **과제 목적에 맞는 복잡도를 유지한다.** 여러 에이전트, 복잡한 인프라, 화면 완성도는 해결 성능에 필요할 때 추가한다.

## 4. 학습 축과 완료 증거

| 학습 축 | 연습 내용 | 완료를 판단할 결과물 |
| --- | --- | --- |
| ① 상황 복원과 문제 선택 | 인터뷰의 사실·의견·요구 구분, 이해관계자 충돌, 추가 질문, 해결 범위 | 근거가 붙은 문제 정의서 |
| ② 정보와 규칙 구조화 | 분산 정보 연결, 시점·상태 관리, 자연어 조건을 판단 절차로 변환 | 데이터 표·규칙표 |
| ③ 에이전트 작동 설계 | 역할 배분, 입력·출력·도구·중단 조건, 예외 처리 | 워크플로와 작동 명세 |
| ④ 구현과 실행 | 흐름 연결, 실제 입력 실행, 누락·오류 처리 | 실행 가능한 최소 에이전트와 실행 기록 |
| ⑤ 검증과 개선 | 성공 기준, 테스트 사례, 실패 분류, 수정 전후 비교 | 테스트 결과와 개선 기록 |

워크플로 예시: 구매 상품·보관 조건·배송 지역 입력 → 배송 규칙 조회 → 가능 여부 판단 → 접수 위치와 방법 안내. 필요한 정보가 없으면 추가 질문하고, 규칙이 충돌하면 확인이 필요한 항목과 담당자에게 넘길 내용을 제시한다.

이 예시는 가상 학습 예시이며, 교동마을의 실제 운영 사실이나 정답이 아니다.

## 5. 기본 학습 사이클과 제출물

**인터뷰 → 근거 정리 → 문제 선택 → 작동 설계 → 구현 → 테스트 → 수정** 순서로 진행한다. 테스트 결과가 문제 정의의 오류를 보여주면 앞 단계로 돌아간다.

전체 사이클 제출물은 다음 네 가지다.

### A. 문제 정의

- 대상 사용자와 상황
- 사용자가 달성하려는 목표와 현재 어려움
- 근거 ID 또는 원문 위치
- 사실, 해석, 미확인 가정의 구분
- 해결할 문제와 제외할 범위
- 성공 기준과 확인 방법
- 추가 질문 및 질문을 멈춘 이유

### B. 작동 구조

- 입력 정보와 필수·선택 항목
- 참조 자료, 규칙, 우선순위
- 단계별 AI·도구·사람의 역할
- 조건별 판단과 행동
- 출력 형식과 근거 표시 방식
- 정보 누락, 충돌, 도구 실패, 범위 밖 요청에 대한 대응
- 재시도, 중단, 사람 확인 조건

### C. 실행 결과

- 실행 방법 또는 재현 가능한 설정
- 실제 사용한 입력과 실제 출력·행동
- 사용 도구와 구현 범위
- 미구현·모의 실행·수동 처리 부분의 명시

### D. 검증 기록

- 테스트 ID, 입력, 사전에 정한 기대 결과, 실제 결과, 통과 여부
- 실패 원인과 수정 내용
- 같은 조건에서의 수정 전후 비교
- 수정 후 확인한 새 사례와 기존 사례의 회귀 확인
- 남은 한계와 다음 개선 우선순위

실제 결과를 확인하지 못했다면 ‘미실행’ 또는 ‘확인 불가’로 기록한다. 실행한 것처럼 작성하지 않는다.

## 6. 예시 문제 출제 규칙

### 6.1 출제 전에 정할 것

출제자는 다음 항목을 먼저 정하고, 학습자에게 공개할 내용을 문제에 포함한다.

- 문제 ID와 적용한 공통 규칙 버전
- 전체 사이클 또는 부분 과제 여부
- 이번 과제의 학습 목표와 평가 대상
- 제한 시간, 허용 도구, 구현 수준
- 제공 자료와 자료별 ID
- 학습자가 추가 질문할 수 있는 방식
- 제출물과 완료 조건
- 공개 테스트와 별도 검증 사례의 구분

자료, 조건, 채점 기준은 답안을 본 뒤 소급해서 추가하지 않는다. 문제 오류를 발견하면 정정 내용을 공개하고 영향을 받은 평가를 다시 한다.

### 6.2 전체 사이클 문제에 넣을 요소

- 입장과 이해관계가 다른 인물들의 인터뷰
- 표면적인 요구와 실제 행동 사이의 차이
- 일부 누락되거나 충돌하는 정보
- 판단에 중요한 단서와 중요도가 낮은 정보
- 적용해야 할 운영 규칙과 우선순위
- 정상 입력과 예외 입력

부분 과제에서는 학습 목표에 필요한 요소만 선택한다. 함정을 많이 넣는 것 자체를 목표로 삼지 않는다.

### 6.3 공정한 문제 구성

- 연습용 인물·수치·규칙은 가상 자료라고 명시한다.
- 검증 사례는 새로운 입력을 사용할 수 있지만, 공개하지 않은 규칙을 정답 조건으로 삼지 않는다.
- 자료로 결론을 낼 수 없는 경우에는 추가 질문·판단 보류·사람 확인도 적절한 행동으로 인정한다.
- 출제자가 예상한 기능과 달라도, 근거·범위·실행·검증이 타당하면 인정한다.
- 정보가 충돌할 때는 적용할 우선순위가 제공되거나, 충돌을 발견하고 확인하는 행동이 허용되어야 한다.
- 가상 인물의 후속 답변은 사전에 정한 사실표와 일관되게 제공한다. 답안을 특정 해결책으로 유도하기 위해 사실을 바꾸지 않는다.
- 학습자가 요청하지 않은 모범답안은 먼저 공개하지 않는다. 평가 기준은 공개하되, 검증 입력과 해설은 별도로 관리한다.

## 7. 답안 피드백 규칙

### 7.1 평가 방식

아래 판정은 공식 점수나 대회 등수 예측이 아니다. 각 항목은 **충족 / 부분 충족 / 미충족 / 확인 불가 / 해당 없음**으로 판단한다.

- 충족: 요구를 만족하는 구체적인 증거가 있다.
- 부분 충족: 일부는 확인되지만 중요한 누락이나 오류가 있다.
- 미충족: 요구와 충돌하거나 필수 내용이 빠졌다.
- 확인 불가: 실행 기록 등 판단에 필요한 증거가 부족하다.
- 해당 없음: 이번 부분 과제에서 요구하지 않은 항목이다.

점수가 필요하면 문제 출제 시 별도 배점을 공개한다. 이 문서만으로 임의의 공식 배점이나 합격 기준을 만들지 않는다.

| 평가 항목 | 판단 질문 | 확인할 증거 |
| --- | --- | --- |
| 문제 선택 | 실제 어려움을 근거로 정의했는가? | 인터뷰 근거, 대안 문제와 선택 이유, 해결 범위 |
| 정보·규칙 구조화 | 누락·충돌·시점·우선순위를 처리했는가? | 데이터 표, 규칙표, 미확인 항목 |
| 작동 설계 | 입력부터 판단·행동·출력까지 연결되는가? | 단계, 조건, 역할, 도구, 예외·중단 조건 |
| 구현·실행 | 설계한 행동이 실제로 수행되는가? | 재현 가능한 설정, 실행 기록, 실제 출력 |
| 검증·개선 | 실패를 발견하고 근거 있게 고쳤는가? | 기대 결과, 테스트 결과, 원인 분류, 전후 비교 |
| 문제 해결 | 사용자가 목표를 달성하거나 다음 행동을 할 수 있는가? | 목표와 연결된 결과, 사용자 행동에 필요한 안내 |

### 7.2 피드백 작성 순서

1. **판정 요약:** 현재 단계에서 확인된 수준과 가장 큰 문제를 먼저 말한다.
2. **근거:** 답안의 문장·설계·실행 기록과 제공 자료를 연결한다.
3. **잘한 점:** 구체적으로 효과가 확인되는 선택을 설명한다.
4. **개선점:** 어디가 왜 부족하며 결과에 어떤 영향을 주는지 설명한다.
5. **수정 우선순위:** 먼저 고칠 항목과 다음 항목을 구분한다.
6. **다음 행동:** 수정하거나 실행할 작은 과제와 재확인 방법을 제시한다.

피드백 표는 다음 형식을 사용한다.

| 항목 | 판정 | 답안·자료 근거 | 수정할 내용 |
| --- | --- | --- | --- |
| 평가 항목명 | 충족 등 | 문장, 자료 ID, 테스트 ID | 구체적인 다음 행동 |

### 7.3 피드백의 제한

- 제출하지 않은 행동·성과·역량을 추측하지 않는다.
- 문장이 매끄럽다는 이유로 구현이나 검증이 우수하다고 판단하지 않는다.
- 단일 정답에 맞추기보다 근거와 작동의 타당성을 평가한다.
- 실행 환경에 접근할 수 없으면 결과의 사실 여부를 확인할 수 없다고 명시한다.
- ‘프롬프트를 더 자세히 써라’와 같은 추상적인 조언 대신 수정할 규칙·입력·단계를 지정한다.
- 문제의 요구와 평가자의 추가 제안을 구분한다. 추가 제안은 감점 근거로 사용하지 않는다.
- 원칙적으로 먼저 학습자가 수정할 기회를 준다. 요청하면 모범답안이나 수정 예시를 제공한다.

## 8. 테스트와 실패 분석

### 8.1 두 층의 검증

| 검증 층 | 확인할 질문 | 가상 배송 과제 예시 |
| --- | --- | --- |
| 작동 검증 | 데이터와 규칙에 맞게 처리했는가? | 배송 불가 지역을 정확히 판별했는가? |
| 문제 해결 검증 | 사용자가 실제 다음 행동을 할 수 있는가? | 어디서 어떻게 접수할지 안내했는가? |

### 8.2 기본 테스트 유형

전체 사이클에서는 다음 다섯 유형을 포함한다. 적용되지 않는 유형은 이유를 기록한다.

1. 정상적으로 처리 가능한 입력
2. 필요한 정보가 빠진 입력
3. 자료끼리 충돌하는 입력
4. 조건의 경계에 해당하는 입력
5. 해결 범위를 벗어난 입력

도구를 사용하면 도구 실패 사례를 추가한다. 외부 문서를 처리하면 문서 속 지시를 따르지 않고 자료로 처리하는지도 확인한다.

성공 기준과 기대 결과는 테스트 전에 정한다. 정답이 하나가 아닌 과제는 허용 가능한 행동과 금지되는 오류를 명시한다. 측정한 결과의 건수·조건·한계를 함께 기록하고 소수 테스트의 통과를 일반적인 성능으로 확대하지 않는다.

### 8.3 실패 원인 분류

| 분류 | 확인할 질문 |
| --- | --- |
| 문제 정의 | 애초에 다른 문제를 해결하고 있지 않은가? |
| 입력 데이터 | 누락·오독·시점 오류·근거 없는 정보가 있는가? |
| 판단 규칙 | 조건·우선순위·경계·예외 처리가 잘못되었는가? |
| 도구 실행 | 잘못된 도구 선택, 호출 실패, 계산·파싱 오류가 있는가? |
| 출력 전달 | 답이 맞더라도 행동에 필요한 안내나 근거가 빠졌는가? |

수정할 때는 가설과 변경 대상을 기록한다. 가능하면 한 번에 한 원인을 수정한다. 여러 변경이 필요하면 묶어서 수정한 이유를 기록한다.

## 9. 전년도 문제 활용 원칙

전년도 8문제를 모두 재현하기보다 올해 필요한 기술을 과제에 연결한다.

| 전년도 문제 | 가져올 훈련 | 올해 연결 지점 |
| --- | --- | --- |
| 인수인계 | 분산 정보 연결, 시점·상태·근거 관리 | 인터뷰로 실제 상황 복원 |
| AI 입국 심사관 | 규칙 구조화, 우선순위, 예외 처리 | 조건에 따른 에이전트 판단 |
| 몽타주를 그려라 | 피드백 해석, 변수 선택, 반복 실험 | 실패 결과를 보고 개선 |
| 춘식도락 메뉴 분석 | 이미지·문서 구조화, 계산 | 입력 정리와 정확한 처리 |
| 영상 팩트 체크 | 답과 근거 연결, 원본 대조 | 출처 확인 가능한 응답 |
| 고대 유적의 비밀 | 추론과 실제 실행 구분 | 도구 선택과 호출 |
| 전투 시뮬레이션 | 검증 사례 분리, 성능 측정 | 새 사례에서도 작동하는지 확인 |
| PDF 스텔스 텍스트 | 문서 내용과 지시 구분, 입력 검사 | 외부 자료 처리의 신뢰성 |

주요 훈련은 인수인계·입국 심사·몽타주에서 가져온다. 다른 문제의 기술은 문서 추출이나 계산 등 실제 과제에 필요할 때 짧게 연습한다.

## 10. 운영 계획: 조정 가능한 항목

이 절은 고정 원칙이 아닌 초기 운영안이다. 학습 기록을 보고 일정·도구·과제 난이도를 조정할 수 있다.

### 10.1 네 단계

| 단계 | 핵심 목표 | 주요 활동 | 종료 결과물 |
| --- | --- | --- | --- |
| 1. 전체 과정 경험 | 작은 사례로 끝까지 완주 | 인터뷰 분석 → 단일 목적 에이전트 → 테스트 | 실행 가능한 첫 버전 |
| 2. 판단의 정확성 | 충돌·규칙·누락 처리 | 추가 질문, 규칙표, 도구 연결, 예외 처리 | 근거와 규칙에 따라 작동하는 버전 |
| 3. 검증과 개선 | 처음 보는 사례에 대응 | 별도 검증, 실패 분류, 수정 전후 비교 | 성능·한계가 확인된 버전 |
| 4. 대회 모의 실행 | 제한 시간 안에 완성·제출 | 새 상황으로 전체 과정, 우선순위, 제출 점검 | 제출 가능한 결과물과 설명 |

각 단계는 약 한 주의 사이클을 기본으로 하되 실제 남은 시간과 진행 속도에 맞춘다. 대회 직전에는 새로운 기술보다 모의 실행과 오류 수정에 집중한다.

### 10.2 세션 구성

가능 시간: 평일 주 2~3회, 회당 1~2시간 / 주말 필수 1회, 3~4시간. 필요하면 주말 1회를 추가한다.

| 세션 | 역할 |
| --- | --- |
| 평일 1회차 | 인터뷰·자료 분석, 문제와 성공 기준 결정 |
| 평일 2회차 | 작동 설계, 구현, 첫 실행 |
| 평일 선택 3회차 | 막힌 기술 보완 또는 실패 수정 |
| 주말 필수 | 여러 사례 테스트, 개선, 결과물 정리 |
| 추가 주말 | 모의 대회 또는 미완성 구현 마무리 |

주력 제작 환경 하나를 정한다. 다른 AI 도구는 자료 분석·코드 검토 등 역할이 분명할 때 보조로 사용한다. 대회 제작 환경이 확인되면 구현 방식을 조정한다.

우선순위는 단일 목적 에이전트 완성 → 규칙·도구·예외 처리 연결 → 새 사례 검증·개선 → 필요한 자동화 확대 순이다.

매주 실행 결과와 검증 기록으로 다음 질문에 답한다.

> 이번 에이전트가 어떤 문제를 해결했고, 그걸 무엇으로 확인했나?

## 11. GitHub와 IDE에서의 적용

권장 저장 위치는 저장소 루트의 `STUDY_RULES.md`다. 문제·답안·피드백마다 이 문서의 버전을 기록한다.

이 파일을 저장소에 올리는 것만으로 모든 IDE나 새 채팅의 AI가 자동으로 읽는 것은 아니다. 사용하는 도구의 프로젝트 지침 또는 세션 시작 요청에 아래 지시를 추가한다. 도구가 지원하는 경우 `AGENTS.md` 같은 지침 파일에서 이 문서를 참조할 수 있다.

```text
작업 전에 저장소 루트의 STUDY_RULES.md를 읽어라.
예시 문제 출제, 스터디 진행, 답안 피드백은 이 문서를 공통 기준으로 적용하라.
적용한 문서 버전과 이번 작업의 평가 범위를 명시하라.
문서에 접근할 수 없다면 읽었다고 가정하지 말고 해당 파일의 제공을 요청하라.
답안을 본 뒤 평가 기준이나 가상 자료의 사실을 임의로 바꾸지 마라.
```

문제 출제 요청 예시:

```text
STUDY_RULES.md를 읽고 [단계/학습 축]을 훈련하는 예시 문제를 만들어줘.
학습 시간은 [시간], 구현 환경은 [환경]이야.
공개할 자료·평가 범위·제출물을 제시하고, 모범답안은 먼저 공개하지 마.
```

답안 피드백 요청 예시:

```text
STUDY_RULES.md와 해당 문제의 공개 조건을 기준으로 내 답안을 평가해줘.
판정·근거·수정 우선순위·다음 테스트를 제시해줘.
실행 기록이 없는 내용은 확인 불가로 표시하고, 아직 요구하지 않은 단계는 평가하지 마.
```

한 문서를 공통 기준으로 유지하고, 개별 문제·답안·피드백·일정은 별도로 관리한다. 공통 규칙에 매회 결과를 덧붙여 문서를 계속 키우지 않는다.

## 12. 변경 관리

- 세션 도중 공통 원칙을 임의로 수정하지 않는다.
- 수정은 사용자 승인 후 별도 Git 커밋으로 남긴다. 수정 이유와 영향 범위를 기록한다.
- 원칙이나 평가 의미가 달라지면 주 버전, 운영 항목이나 기준을 추가하면 부 버전, 의미가 바뀌지 않는 문구 정정은 패치 버전을 올린다.
- 기존 답안은 원칙적으로 당시 적용한 버전으로 평가한다. 새 버전으로 재평가하면 그 사실을 명시한다.
- 공식 환경·규정이 달라지거나 반복해서 불공정한 평가가 발생하면 변경을 검토한다.

‘변하지 않는 규칙’은 영구적으로 수정 불가능한 문서가 아니라, **임의로 흔들리지 않으며 변경 이력이 남는 기준**을 의미한다.

| 버전 | 날짜 | 변경 내용 |
| --- | --- | --- |
| 1.0.0 | 2026-10-06 | 새 스터디 방향을 출제·진행·피드백 공통 규칙으로 정리 |
